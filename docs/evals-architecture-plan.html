Architecture Plan

End-to-end evals for the camelAI agent

Build a headless evaluation system that provisions real workspaces, runs the existing agent loop through ChatThreadDO.externalMessage, captures artifacts and transcripts, and scores outcomes with deterministic checks plus judge models where needed.

Headless turns Workspace fixtures Artifact capture Human review CI-ready

Recommendation

Start with a Worker + DO runner, not browser automation.

The fastest reliable path is to treat evals as an internal producer of chat turns. We already have the needed primitive: WorkspaceCronDO calls ChatThreadDO.externalMessage and waits for a finished turn. Evals should add orchestration around that primitive: setup a workspace, create a thread, send the prompt, wait for the result, inspect the workspace, score it, and persist the run.

Browser automation should be reserved for product UI evals. Agent capability evals should use the same Durable Object path as Slack, email, cron, and other non-browser channels so failures point at the agent/runtime, not at Playwright timing.

Current Leverage Points

Agent turn API

ChatThreadDO.externalMessage accepts thread, workspace, org, user, message, and timeout context, then resolves with result, busy, question, or error.

Headless precedent

WorkspaceCronDO already dispatches prompt runs to ChatThreadDO without a browser and persists run status. Evals can reuse this pattern with stricter isolation and artifacts.

Sandbox lifecycle

sandbox-host owns workspace directories, Docker/gVisor containers, file operations, shell exec, and transcript retrieval. Eval setup and grading should go through these explicit APIs.

1

2

Execution Flow

  1. Load suite. Validate the suite file against a schema, expand matrix options, and compute stable case hashes.
  2. Create eval run. Store run metadata in EvalRunDO SQLite and emit an observability event with suite, case count, branch, commit, and model.
  3. Provision workspace. Create an eval workspace in a dedicated org, seed fixtures through sandbox-host file APIs, and warm the container only when the first turn starts.
  4. Create thread. Use the same thread metadata path as product threads, with created_by = "eval-runner" and explicit model selection.
  5. Send turn. Call ChatThreadDO.externalMessage with a long timeout and no browser clients. If the agent asks the user a question, auto-answer "unavailable" and mark the case as requiring product/rubric review.
  6. Collect artifacts. Read the final assistant response, transcript messages, workspace file tree, selected files, command logs, previews, published app metadata, and usage.
  7. Score. Run deterministic checks first. Run model judges only after deterministic collection succeeds, and save judge prompts and outputs as artifacts.
  8. Summarize. Produce per-case result JSON, aggregate suite metrics, CI output, and a human review URL.

Scoring Strategy

Deterministic first

Prefer command exit codes, file presence, typecheck, tests, route responses, database rows, and published app probes. These are stable and cheap.

Model judges second

Use judge models for subjective quality: UX fit, instruction following, explanation quality, and whether the final answer is useful. Store all judge inputs and outputs.

Human calibration

Add a small review UI so humans can override or calibrate judge scores. Keep human labels as separate ground truth, never overwrite raw judge output.

Storage and Observability

Persistent state

  • EvalRunDO SQLite: run, case, attempt, score, and artifact index rows.
  • R2: transcripts, workspace tarballs or sparse snapshots, diffs, screenshots, judge traces, command logs.
  • Admin index: latest suite summaries and trend data for dashboards.

Operational events

  • Use recordObservabilityEvent for run start, case start, turn complete, score complete, and failures.
  • Include ids, model, billing source, usage provider, duration, status, token counts, and artifact sizes.
  • Do not store request bodies, secrets, auth headers, or full transcripts in Analytics Engine.

Implementation Phases

Phase Scope Exit criteria
1. Local MVP Add suite schema, local CLI, workspace seeding, thread creation, externalMessage dispatch, transcript/artifact capture, and deterministic checks. One command runs 5 smoke cases locally or against staging and emits JSON.
2. Durable runner Add EvalRunDO, admin API, R2 artifacts, run cancellation, retries, and observability. Runs survive Worker restarts and can be inspected after completion.
3. Judging Add rubric judges, pairwise comparison, judge prompt versioning, score aggregation, and human override metadata. Each subjective case has raw judge traces and reproducible aggregate scores.
4. CI and dashboard Add GitHub Actions integration, trend reports, baseline comparison, and a small admin review surface. PRs can run smoke evals; nightly suites produce trend lines and regressions.

Key Decisions

Use real workspaces

Evals should run against the actual workspace and container stack. Mocking the sandbox would miss most failures that matter: file paths, package managers, tool wiring, preview publishing, and transcript conversion.

Keep eval orgs isolated

Use a dedicated eval org, eval users, and workspace naming prefix. This keeps billing, admin listing, retention, and cleanup tractable.

Make every artifact addressable

A score without a replay path is not useful. Each case needs links to the prompt, transcript, workspace snapshot, checks, judge payloads, and final assistant answer.

Separate capability and UI evals

The headless path should be the default. Browser-driven evals should be their own suite type for visual workflows, not a dependency of all agent grading.

Risks and Mitigations

Long-running turns

Use per-case timeouts, heartbeats, cancellation, and attempt state. Keep the default high enough for real app builds but visible in run summaries.

Judge drift

Version judge prompts and models. Keep deterministic checks as the pass/fail backbone, and compare judge score distributions over time.

Cost blowups

Add suite budgets, concurrency limits, token/credit reporting, and fail-fast thresholds for broken builds or unavailable models.

Important: Do not make eval setup silently recover from failed workspace seeding, fixture loading, or scoring commands. Those should fail the case loudly with preserved diagnostics.

First Build Slice

  1. Add evals/schemas.ts and evals/suites/smoke.yaml.
  2. Add scripts/run-evals.ts that can run one case against local dev or staging.
  3. Add an internal helper that creates an eval thread and calls ChatThreadDO.externalMessage.
  4. Capture transcript through existing admin/thread message paths and workspace files through sandbox-host FS APIs.
  5. Implement four deterministic assertions: command, file exists, file contains, HTTP probe.
  6. Write result JSON to .eval-results/ locally; defer R2 until the durable runner phase.
