Channels Architecture

A provider-neutral ingress layer for Slack, email, Telegram, and future messaging surfaces. Provider adapters own transport details; the channel core owns identity, thread mapping, model selection, turn dispatch, and provider-owned outbound tools.

Inbound providers

Parses MIME, validates workspace mailbox, checks sender access, uploads inbound attachments, and sends outbound files through the send_email tool.

Runtime and replies
ChatThreadDO

Normal message enqueue

Channel turns enter the same message path as UI chat messages: prepend a hidden <camelai system message> naming the correct outbound tool, enqueue user content, stream/run the agent, and persist thread metadata.

Sandbox runtime

Agent execution

Uses the same container, tools, history, browser prompts, and usage accounting as web chat.

provider tools

Agent-controlled outbound

Each provider registers its own tools, such as send_email, send_slack_message, or send_telegram_message. There is no generic channel reply tool, and the hidden channel system message tells the agent which provider tool to use. Attachments are explicit tool inputs using /mnt/user-uploads or /mnt/user-outputs paths.

The runner does not wait for a provider reply payload. Final assistant text stays internal; provider messages are sent only when the agent calls the provider-specific outbound tool named in the hidden channel system message.

What stays provider-specific

Signature verification, OAuth/install lookup, email MIME parsing, Slack event semantics, Telegram webhook security, attachment fetching, and outbound tool execution.

What becomes shared

Dedupe key shape, external conversation to thread mapping, default model selection, thread creation, turn dispatch, and normalized tool registration context and shared guardrails for provider-owned outbound tools.

No implicit replies

The channel runner does not send the final assistant message back to the provider. This prevents accidental emails/posts and forces outbound communication through explicit provider tools.

Runner simplicity

A channel message should behave like a normal user message from the browser UI. The only additions are channel origin metadata and provider-specific outbound tools in the agent toolset.

Thread origin

Threads started from channels are queryable as channel-originated threads, with channel_kind, channel_connection_id, channel_conversation_id, and first channel message metadata.

Attachments both ways

Inbound files are normalized into workspace upload paths. Outbound provider tools accept explicit attachment paths and send them using Cloudflare Email Sending, Slack external upload, or Telegram documents.

Clean start

Channels are the source of truth from day one. Slack, email, Telegram, and future providers all start from the same channel contract.

Email adapter

Mailbox routing, sender membership, MIME parsing, inbound attachment R2 uploads, Cloudflare Email Sending-backed send_email attachments.

Slack adapter

Signing secret, event queueing, installation lookup, bot mention rules, private file download, external upload-backed send_slack_message attachments.

Telegram adapter

Webhook secret, bot token, chat ID mapping, media download, sendDocument-backed send_telegram_message attachments.

Channel core

Stable channel IDs, dedupe, thread mapping, thread origin metadata, model defaults, external turn dispatch, provider tool context.

Target design: inbound channel turns are passive by default; outbound provider messages require explicit provider-specific tool calls.
